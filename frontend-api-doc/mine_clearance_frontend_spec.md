# 排雷兵（Mine Clearance）前端设计与开发说明

> **文档用途：** 提供给前端开发 Agent，作为项目页面设计、前端架构搭建和演示版开发的执行依据。  
> **项目阶段：** 前端先行设计；后端仍在开发中。当前优先完成可交互演示版，后续通过替换 Mock 数据层接入真实后端。  
> **设计方向：** 浅色、专业、简洁、清晰，偏企业级产品。

---

## 1. 项目定位与前端目标

“排雷兵”是一个围绕代码审查能力训练展开的平台。用户在训练过程中阅读代码、识别潜在问题、提交审查意见，并与 AI 进行交互或对抗，最终获得训练结果和能力反馈。

前端不应将产品设计成普通的 AI 聊天网页，而应突出以下体验：

1. **代码审查工作台：** 让用户能够清楚地阅读代码、提交审查意见、查看必要证据。
2. **AI 对抗训练：** 通过 AI 交互体现训练过程，而不是简单的一问一答。
3. **能力评估与成长：** 训练结束后呈现每道题的评估结果、理由和改进建议，并保留历史记录。

前端当前有两个目标：

- **演示目标：** 在后端尚未完成时，能够完整演示“登录 → 创建训练 → 完成训练 → 查看报告 → 查看历史”的流程。
- **后续开发目标：** 页面、组件、数据类型和 API 调用分层清晰，后端完成后尽量只替换数据服务，不大规模重写页面。

## 2. 设计原则

- 浅色专业风格，整体简洁、清晰，避免过度装饰。
- 以信息层级和操作效率为优先，训练工作台是核心页面。
- 组件化开发，统一按钮、卡片、表格、输入框、状态标签等基础样式。
- 页面必须考虑加载中、空数据、失败、服务不可用等状态。
- Mock 数据必须明确标记为演示数据，不能伪装成真实后端数据。
- 前端只负责展示和交互；训练状态、题目内容、证据权限、评分结果和调用预算最终以服务端为准。

## 3. 视觉设计规范

### 3.1 色彩

建议使用以下基础色值，允许在实现时小幅调整，但要保持统一：

| 用途 | 色值 |
|---|---|
| 页面背景 | `#F5F7FA` |
| 卡片背景 | `#FFFFFF` |
| 主色 / 主要操作 | `#2563EB` |
| 主要文字 | `#172033` |
| 次要文字 | `#667085` |
| 边框 | `#E4E7EC` |
| 成功状态 | 低饱和绿色 |
| 警告状态 | 低饱和琥珀色 |
| 错误状态 | 低饱和红色 |

### 3.2 组件外观

- 卡片圆角：约 10–12px。
- 按钮、输入框圆角：约 8px。
- 卡片以白色为主，使用细边框和轻微阴影区分层级。
- 页面留白充足，不要把所有信息堆在一个区域。
- 状态色应低饱和，避免大面积高亮色。
- 图标风格统一，优先使用线性图标。

### 3.3 响应式

优先保证桌面端体验。窄屏时：

- 左侧导航栏折叠为图标栏或移动端菜单。
- 训练工作台不要强行挤压成三列，改为标签页或分区切换。
- 表格允许横向滚动，关键操作保持可见。

## 4. 页面路由与布局

建议使用 React Router 管理路由。

| 路由 | 页面 | 说明 |
|---|---|---|
| `/login` | 登录页 | 演示入口，不做真实账号验证 |
| `/dashboard` | 首页 / 工作台 | 平台概览、开始训练、最近训练 |
| `/training/setup` | 训练配置页 | 选择训练语言和训练方向 |
| `/training/:id` | 训练工作台 | 核心训练交互页面 |
| `/report/:id` | 训练报告页 | 展示训练结果和反馈 |
| `/history` | 训练历史页 | 查询和查看历史训练 |
| `/analytics` | 能力分析页 | 展示能力维度与趋势 |
| `/system` | 系统状态页 | 展示服务状态和调用情况 |

### 4.1 登录页 `/login`

**目标：** 提供简单、完整的演示入口，不实现真实身份认证。

布局建议：

- 页面采用左右分栏。
- 左侧：项目名称“排雷兵 / Mine Clearance”、一句产品介绍、简短功能说明或抽象视觉元素。
- 右侧：登录卡片，展示演示身份信息和“进入平台”按钮。
- 点击“进入平台”直接跳转到 `/dashboard`。
- 不需要真实账号密码校验；不要让用户因为输入错误而无法进入演示。

### 4.2 首页 `/dashboard`

**目标：** 让用户进入平台后快速理解当前状态，并开始一次训练。

布局建议：

1. 顶部导航：项目 Logo / 名称、页面入口、用户演示身份。
2. 欢迎区域：简短欢迎语和“开始新训练”主按钮。
3. 数据概览卡片：
   - 已完成训练次数
   - 已审查题目数
   - 训练任务数或近期训练情况
   - 服务状态
4. 推荐训练区域：展示可开始的训练方向或训练任务。
5. 最近训练区域：显示最近几次训练、时间、状态和查看报告入口。

注意：演示数字必须标注为演示数据，不能让用户误认为是真实统计。

### 4.3 训练配置页 `/training/setup`

**目标：** 在开始训练前选择训练参数，并向用户说明训练规则。

布局建议：

- 页面标题和简短说明。
- 语言选择卡片或下拉框：Python、Java、C、C++（具体可用范围待后端确认）。
- 训练方向选择：
  - 随机训练
  - 逻辑与边界问题
  - API 使用问题
  - 安全与性能问题
- 训练规则说明卡片。
- 页面底部提供“开始训练”按钮。

**重要业务约束：**

- 每次训练固定 3 道题。
- 每道题最多 3 轮交互。
- 每次训练最多 12 次在线模型调用。

不要将题目数量、每题轮数或模型调用上限设计成用户可以随意修改的配置项。具体语言、训练方向是否全部支持，以后端最终接口为准；后端未确认前可以在 Mock 模式展示，但应方便调整或禁用选项。

### 4.4 训练工作台 `/training/:id`

<badge>核心页面</badge>

**目标：** 这是整个产品最重要的页面。用户在这里阅读代码、提交审查意见、查看 AI 反馈并完成训练。

桌面端建议采用三栏布局：

- 左侧：题目导航与训练进度。
- 中间：代码阅读区域。
- 右侧：AI 对话 / 对抗交互区域。
- 底部或可折叠区域：证据与引用信息。

#### 顶部状态栏

展示：

- 当前训练名称或 ID
- 当前题目序号（例如第 1 / 3 题）
- 当前轮次
- 整体训练进度
- 训练状态
- 返回或退出训练入口

#### 左侧：题目导航

- 展示本次训练的 3 道题目。
- 标明当前题、已完成题和未开始题。
- 展示整体进度。
- 题目切换应遵循后端定义的训练流程，不能通过前端操作绕过服务端状态。

#### 中间：代码面板

- 使用代码编辑器组件展示代码，建议采用 Monaco Editor。
- 第一阶段以只读代码展示为主。
- 支持语法高亮、行号、滚动、复制；如实现代码选中，应能将选中内容作为审查上下文提交。
- 根据题目语言切换语法高亮。
- 代码区域应有清晰标题和必要的文件信息。

#### 右侧：AI 交互面板

- 展示 AI 的交互内容。
- 提供审查意见输入框和提交按钮。
- 展示用户提交内容、AI 回复、轮次信息。
- 如后端支持流式响应，再实现逐步输出效果；后端未确认前不要把 SSE 当作既定能力。
- 提交过程中显示加载状态，避免重复提交。
- 请求失败时显示可理解的错误提示，并根据后端规则提供重试方式。

#### 底部 / 可折叠：证据面板

- 展示后端允许用户查看的证据 ID、引用片段或说明。
- 证据内容必须来自后端明确授权返回的数据。
- 证据项应能与代码位置或审查意见建立关联（若后端提供对应字段）。

#### 训练过程中的信息边界

**在当前题目结算前，不得向用户泄露：**

- 正确答案；
- 被植入的问题或缺陷的具体位置与差异；
- 触发条件；
- 修复方案或标准修复代码。

前端只能展示当前训练阶段允许展示的信息。证据面板必须采用后端返回的白名单数据，不要通过前端自行推断或拼接隐藏信息。

### 4.5 训练报告页 `/report/:id`

**目标：** 训练结束后，完整呈现本次训练表现。

建议布局：

1. 报告头部：训练名称、完成时间、训练状态。
2. 总体概览：完成题目数、交互情况、模型调用情况（仅当后端提供）。
3. 分题结果卡片：每题单独展示评估等级、评估理由和相关交互。
4. 审查过程：展示用户提交的审查意见、AI 对抗过程及证据校验结果（以服务端允许返回的内容为准）。
5. 改进建议：给出可执行的审查能力提升建议。
6. 页面底部：重新训练、返回首页、查看历史等入口。

项目使用的 L0–L4 等级应按项目后端/总体方案中的正式定义展示。当前已知的概念性描述如下，实际文案以项目正式定义为准：

| 等级 | 概念性描述 |
|---|---|
| L0 | 误报、错误归因，或把正常代码判断为缺陷 |
| L1 | 意识到可能存在问题 |
| L2 | 能定位问题 |
| L3 | 能解释问题的触发条件 |
| L4 | 能给出可执行的修复方案 |

不要擅自把 L0–L4 等级简单求平均，生成一个未经定义的“总分”。如果需要综合分数，必须先确认项目是否定义了明确的计算规则。

### 4.6 训练历史页 `/history`

**目标：** 让用户查看过去完成或进行中的训练。

建议使用表格布局，字段包括：

- 训练 ID
- 训练时间
- 训练方向
- 训练状态
- 结果摘要
- 操作（查看报告 / 继续训练，具体取决于后端是否支持）

建议提供：

- 关键词搜索
- 状态筛选
- 日期筛选
- 分页（如数据量需要）

必须设计空状态、加载状态和请求失败状态。

### 4.7 能力分析页 `/analytics`

**目标：** 展示用户在多次训练中的能力变化。

建议内容：

- L0–L4 各等级的题目分布。
- 不同训练方向的表现。
- 训练次数或能力变化趋势。
- 需要加强的能力维度。

注意：

- 必须区分“每题 L0–L4 评估等级”和其他百分比指标。
- 百分比、综合能力分等指标必须有明确的数据定义和计算口径。
- 如果后端尚未提供真实数据，使用明确标注的 Mock 数据，不要暗示为真实用户能力结论。

### 4.8 系统状态页 `/system`

**目标：** 为演示和后续排查提供服务运行状态概览。

建议展示：

- API 服务状态
- 检索服务状态
- 模型服务状态
- 训练会话服务状态
- 当前训练的模型调用预算或调用情况（若接口提供）
- 关键事件或审计记录（若接口提供）

**状态展示要求：**

- Mock 模式应明确标注“演示状态”或“模拟数据”。
- 后端未连接时，不得显示“全部正常”等误导性绿色状态。
- 真实状态必须来自真实健康检查接口。

## 8. Mock 数据与后端接入策略

### 8.1 核心原则

页面组件不要直接散落 `fetch` 请求。统一通过 Service 层获取数据：

- 页面只关心数据和交互状态。
- Service 层决定使用 Mock 还是请求真实 API。
- Mock 和真实 API 尽可能返回相同的数据结构。
- 后端接入时优先替换 Service 实现，不重写页面。

建议使用环境变量切换数据模式：

```env
VITE_DATA_MODE=mock
VITE_API_BASE_URL=http://localhost:8000
```

以上地址仅为开发示例，实际地址以后端部署配置为准。

### 8.2 演示流程

Mock 模式下至少实现以下完整流程：

1. 用户打开登录页。
2. 点击“进入平台”进入首页。
3. 点击“开始新训练”进入训练配置页。
4. 选择语言和训练方向，创建一场训练。
5. 进入训练工作台。
6. 完成 3 道题目的交互流程。
7. 训练结束后进入报告页。
8. 在历史页查看本次训练记录。
9. 刷新页面后，尽可能保留必要的演示状态。

演示内容应具有合理的题目、代码、对话和报告数据，但不要把隐藏答案提前暴露在训练界面中。

### 8.3 后端接口（暂定）

根据当前项目方案，前端可能需要以下接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/v1/health` | 服务健康检查 |
| `POST` | `/v1/sessions` | 创建训练会话 |
| `GET` | `/v1/sessions/{id}` | 获取训练会话 |
| `POST` | `/v1/sessions/{id}/submit` | 提交审查意见 |
| `POST` | `/v1/sessions/{id}/settle` | 结算训练或题目 |
| `GET` | `/v1/evidence/{id}` | 获取证据 |

**以上接口仅为当前方案中的暂定接口清单，不代表后端已实现或最终契约。** 开发时应先将请求和响应类型集中定义；接入真实后端前，必须与后端开发者确认：

- 路径、HTTP 方法和字段名称；
- 请求体、响应体和错误格式；
- 会话状态及题目状态流转；
- 证据接口的权限与可见范围；
- 结算时机和报告数据结构；
- 是否支持 SSE 或其他流式响应方式；
- 分页、重试、超时和鉴权机制。

不要根据暂定接口自行臆造后端字段，也不要把未确认的 SSE 流式能力写成强依赖。

## 9. 关键业务约束与前端边界

以下约束应在前端交互中体现，但最终必须由后端校验：

1. 一次训练固定 3 道题。
2. 每道题最多 3 轮交互。
3. 一次训练最多 12 次在线模型调用。
4. 训练过程中的题目状态、轮次、预算和结算结果以服务端为准。
5. 用户未完成当前题目结算前，不得展示正确答案、缺陷差异、触发条件和修复方案。
6. 证据只能展示后端明确授权返回的内容。
7. 前端的禁用按钮、输入限制和路由控制只是用户体验保护，不能替代后端权限和业务校验。

## 10. 开发阶段建议

### 阶段一：工程骨架与设计系统

- 检查现有仓库和技术栈。
- 建立路由、布局和基础组件。
- 统一颜色、字体、间距、圆角和按钮样式。
- 完成登录页和登录后公共布局。

### 阶段二：静态页面与 Mock 数据

- 完成首页。
- 完成训练配置页。
- 完成训练历史页。
- 完成能力分析页。
- 完成系统状态页。
- 为页面建立统一的数据类型和 Mock Service。

### 阶段三：训练工作台

- 完成代码面板。
- 完成题目导航和训练进度。
- 完成审查意见输入和提交交互。
- 完成 AI 对话展示。
- 完成证据面板。
- 加入加载、错误、重复提交保护等状态。

### 阶段四：完整演示闭环

打通：

`登录 → 首页 → 训练配置 → 训练工作台 → 训练报告 → 训练历史`

确保 Mock 模式下可以从头到尾操作，而不只是静态页面跳转。

### 阶段五：接入真实后端

- 与后端确认 API 契约。
- 实现真实 Service。
- 保持页面尽可能不变。
- 完善鉴权、异常处理、请求取消、超时和会话恢复。
- 仅在后端确认支持时实现 SSE 等流式能力。

## 11. 验收标准

开发完成后，至少满足以下标准：

### 视觉与布局

- [ ] 整体为浅色、专业、清晰的企业级风格。
- [ ] 页面间距、卡片、按钮、文字和状态样式统一。
- [ ] 桌面端布局完整，窄屏下没有严重错位或溢出。
- [ ] 训练工作台的信息层级清晰，代码区域有足够空间。

### 页面与交互

- [ ] 登录页点击按钮即可进入平台，不依赖真实账号验证。
- [ ] 首页可以进入训练配置。
- [ ] 训练配置可以创建 Mock 训练。
- [ ] 训练工作台能够完成三道题的演示交互。
- [ ] 训练完成后可以查看报告。
- [ ] 历史页能看到已完成的 Mock 训练。
- [ ] 分析页和系统页具有合理的演示数据与状态说明。

### 架构与业务边界

- [ ] 页面组件不直接耦合 Mock 数据。
- [ ] Mock 与真实 API 通过 Service 层切换。
- [ ] 关键数据结构有 TypeScript 类型。
- [ ] 固定题目数、轮次和调用预算在界面中正确体现。
- [ ] 结算前不会泄露答案、缺陷细节、触发条件或修复方案。
- [ ] 证据内容只使用允许展示的数据。
- [ ] 不把未经定义的 L0–L4 平均值当作总分。
- [ ] Mock 状态不会伪装成真实服务健康状态。

## 12. 给开发 Agent 的执行指令

请按以下顺序执行：

1. **先检查当前仓库**：确认是否已有 React、Vite、TypeScript、路由、样式体系和已有组件。不要未经检查就覆盖现有工程。
2. **先输出简短实施计划**：说明准备新增或修改哪些目录、页面和依赖。
3. **优先完成可运行的前端演示版**：不等待后端；使用 Mock Service 完成端到端流程。
4. **严格按本说明实现页面结构和视觉方向**：不要擅自把产品改成普通聊天机器人页面。
5. **保持业务数据可替换**：Mock 数据和真实 API 的调用必须隔离。
6. **不猜测后端契约**：暂定接口只作为接入准备，真实接入前必须核对。
7. **完成后运行项目检查**：至少执行构建；如果仓库配置了 lint 或测试，也应执行并修复明显问题。
8. **最终汇报**：列出已完成页面、主要交互、运行方式、Mock 模式切换方法、尚未实现事项和需要后端确认的问题。

**优先级建议：** 登录页、全局布局、首页、训练配置页、训练工作台、训练报告页优先；历史、能力分析和系统状态页随后完善。最终目标是先得到一个视觉统一、流程完整、方便后端接入的可演示产品。
